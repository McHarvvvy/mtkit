# 测试策略与用例计划 · 输出样板

> 三段式产物示例。被测对象：订单创建 API `POST /orders`，配反向读 `GET /orders/{id}`、`GET /users/{id}/credit`、`GET /users/{id}/orders`、`GET /products/{id}/stock`。

---

## 业务事实清单

> 离开源码，纯业务语言；每条用例须可追溯到此清单某条。

1. 信用 + 库存足够 → 下单成功，再读订单为"已确认"
2. 信用不足 → 拒绝下单，不产生订单
3. 用户服务不可达 → 订单进入"人工审核"，非整体失败
4. 同一幂等键重复提交 → 返回首次结果，不重复扣减
5. 单笔金额必须在 (0, 10000]，精度 ≤ 2 位
6. 下单成功 → 风控系统会收到该订单事件（**业务契约级外部触达**）

> 代码里看到、不在清单里的（"清额度缓存"、"按列拼 SQL"、"logger 输出 order_created"）= 实现机制，不进用例。

## 测试策略摘要

**被测范围**：`POST /orders` 单 endpoint + 4 个配套反向读接口。

**依赖处理**

| 依赖                   | 策略                  | 理由                                        |
| ---------------------- | --------------------- | ------------------------------------------- |
| 用户服务（外部 gRPC）  | fake（可配延迟/超时） | 跨服务，需可控故障注入                      |
| 订单 DB / 库存（内部） | 真实                  | 本服务自有 IO，mock 会让前门验证退化为假绿  |
| 风控 MQ                | fake，具调用记录能力  | 业务契约级触达，需断言"是否触达 + 业务参数" |
| 时间 / 订单 ID         | 注入抽象，用例固定值  | 不可控输入需稳定                            |

**数据策略**：用户 / 商品 fixture 共享；额度、库存、金额、时间内联；金额边界用表格驱动。

**隔离策略**：**数据集合分桶**——每条用例使用独立用户 ID 命名空间，支持并行；不依赖 cleanup。

**风险地图**：信用校验逻辑刚改（变更点）/ 库存并发扣减历史超卖（回归区）/ 金额精度、跨时区、整点优惠（隐式边界）。

## 第三段 · 用例清单

### 维度 1 · 核心业务规则

**TC-01 信用不足拒绝下单**（→ #2）
- 目的：防止信用校验被绕过导致坏账
- Given：用户剩余额度 0；商品 A 库存充足
- When：提交订单 商品 A × 1，金额 600
- Then：响应 `CREDIT_INSUFFICIENT`；`GET /users/{id}/orders` 无此单；`GET /products/{id}/stock` 库存未扣

**TC-02 信用刚够下单成功**（→ #1，三角验证示例）
- 目的：边界——剩余额度等于金额时应放行
- Given：用户剩余额度 600；商品 A 库存 ≥ 1
- When：提交订单 金额 600
- Then：response 返回 `orderID`；`GET /orders/{orderID}` 状态 = `CONFIRMED`；`GET /users/{id}/credit` 余额 = 0
  > 同时验证 response、反向读、联动读三个观察面，关键路径值得做。

### 维度 2 · 异常路径与容错

**TC-07 用户服务超时降级人工审核**（→ #3）
- 目的：防止外部依赖故障导致下单整体不可用
- Given：fake 用户服务在 2s 后超时
- When：提交订单
- Then：响应受理成功；`GET /orders/{orderID}` 状态 = `PENDING_REVIEW`；`GET /products/{id}/stock` 库存未扣

### 维度 3 · 边界条件（数据驱动）

**TC-12~17 金额边界**（→ #5）
- 目的：保护合法区间端点与精度上限
- 接受 / 拒绝以"`GET /orders/{id}` 是否可查到 + response 状态码"双通道判定

| 金额 | 0.00 | 0.01 | 9999.99 | 10000.00 | 10000.01 | 1.005 |
| ---- | ---- | ---- | ------- | -------- | -------- | ----- |
| 期望 | 拒绝 | 接受 | 接受    | 接受     | 拒绝     | 拒绝  |

### 维度 4 · 状态流转与幂等

**TC-20 同 key 重复提交返回首单结果**（→ #4）
- 目的：防止网络重试导致重复扣库存
- Given：同一 `Idempotency-Key` 已成功创建订单 O1
- When：用同 key 再次提交，body 不同
- Then：返回 O1 的结果；`GET /users/{id}/orders` 仅一条；`GET /products/{id}/stock` 仅扣 1

### 维度 7 · 副作用契约（业务文档承诺的外部触达）

**TC-30 下单成功 → 风控收到该订单事件**（→ #6）
- 目的：保护"下单必通知风控"业务契约
- Given：额度与库存充足
- When：提交订单成功返回 `orderID`
- Then：fake 风控收到 `orderID` 匹配的事件，事件含 userID / amount 关键业务参数
- **不**断言：调用次数、重试间隔、字段顺序、协议层细节

### 维度 9 · 事务原子性

**TC-31 风控通知失败 → 整体回滚**（→ #6 反面）
- 目的：防止本地订单已建但风控未通知形成风险敞口
- Given：fake 风控配置为永久失败
- When：提交订单
- Then：响应错误；`GET /users/{id}/orders` 无该订单；`GET /products/{id}/stock` 库存未变

## 为什么不写

- **空字段 / 类型错误校验** — 请求体中间件统一覆盖，本接口仅透传
- **商品不存在** — 库存服务自身契约测试已覆盖
- **HTTP 4xx/5xx 报文壳** — 框架统一封装，无业务分支
- **用户 ID 为 nil / 空** — 网关层校验
- **维度 8 缓存契约独立用例** — 业务无 TTL / `Cache-Control` 对外承诺，反向读用例已覆盖"再读拿到新值"
- **风控"被调用了 1 次"** — 次数是实现，TC-30 已断言触达 + 业务参数
- **DB 字段拼接顺序 / 列名校验** — 实现细节
- **100 并发同金额下单** — 压测范畴，功能用例仅以 2-并发验证锁正确性
- **后门兜底** — 本接口前门 a-d 完整可达（response + 三个反向读 + 风控 fake），无需走后门
