# API 测试策略与用例计划 Skill

> **适用范围**：API 层（HTTP / gRPC handler）——通过真实 HTTP / gRPC 调用、连接真实存储、替换不可控外部依赖来验证。其他层级有各自契约定义，**不在本 skill 范围**。

输出 **业务事实清单 → 测试策略 → 用例清单** 三段式，**只写高价值用例**，不追求覆盖率。

---

## 一、核心哲学（4 条元原则）

> 一切测试本质上是**对所属范围契约的黑盒验收**。unit / integration / acceptance / E2E 只是范围大小不同——"unit"原指"行为单元"，不是"代码单元"。

**原则 1 · 断言只咬契约，setup 可以耦合实现**
fixture 阶段直插 DB / 用 ORM 起数据 / 调内部接口造前置——都是手段，换实现时改 fixture 即可，**assert 一行不动**。问题只发生在 assert 引用了"只有读源码才知道的符号"（cache key 名、表列、调用次数、私有字段、内部错误字符串）。
> 例：缓存命中率 / key 名是机制（不测）；"写后再读拿到新值"是契约（要测）——后者跟"底下有没有缓存"无关。

**原则 2 · 重构韧性是位置正确性的判据**
业务行为没变、只重构内部，这条用例该挂吗？该挂 = 断言写穿到机制层，必须往上抬。**"换实现就崩"的用例，不管绿不绿都是反向价值。**

**原则 3 · 知道实现 ≠ 依赖实现**
朴素自检：盖住源码，光读产品文档能不能写出这条 assert？写不出 = 写穿了。

**原则 4 · 契约面比 response 宽**
对外承诺过的可观察面都算契约：**响应面 / 反向读面 / 联动面 / 副作用面**。常见违反——默认只看 response body，遇 write-only 接口就跳后门：**契约面没穷举完，没资格走后门**。

## 二、通用禁断列表

任何用例 assert **永远不能咬**：

| 禁断对象                 | 原因                                             |
| ------------------------ | ------------------------------------------------ |
| 调用次数 / 顺序          | 机制，非契约                                     |
| 内部 cache key、SQL 列序 | 实现细节                                         |
| 内部错误消息字符串       | 内部表达                                         |
| 内部日志                 | 调试信息（**合规审计日志除外**——产品承诺即契约） |
| 内部分支命中、私有字段值 | 实现状态                                         |
| Response 非契约字段      | 内部新增会拖挂用例                               |

> **snapshot / golden 只对契约面字段比对**；全量 response 序列化是反模式——实现新增字段会让无关用例集体挂。

## 三、工作流程

### STEP 0：信息收集 + 范围圈定

| 场景             | 输入            | 起手动作                           |
| ---------------- | --------------- | ---------------------------------- |
| **A · 代码后补** | 已有功能代码    | 反推契约 / 扫调用面 / 定位变更点   |
| **B · 设计先行** | 需求 + 设计文档 | 梳理契约 / 提取约束 / 对齐验收标准 |

**信息项（缺一必澄清）**：被测对象与契约 / **被测范围**（决定业务事实清单粒度——单 endpoint？CRUD 集合？整个 service？）/ 业务上下文 / 现有覆盖 / 风险信号 / 环境约束（能否起真实 DB / 能否联网）。

### STEP 0.5：业务事实清单（强制门槛）

**离开源码**，问自己：

> 如果只读产品文档 / 接口说明，这个接口对外承诺了什么？

写下 **3-7 条核心业务事实**，纯业务语言：
- ✓ "用户开启 X 后，再读 X 状态返回开启"
- ✓ "未通过密码验证时拒绝关闭 Y"
- ✓ "开户成功后，风控系统会收到该用户的开户事件"（外部触达本身是业务契约时才写）

代码里看到、但不在这清单里的东西（缓存清理、外部编排、SQL 拼装、内部分支）一律记为**实现机制**，不进用例。

> **为什么强制**：跳过会把代码里的每个分支误当成"风险点"，写出测调用次数 / 测 cache key 的用例。**这是源头过滤器。**

## 四、测试策略要素

### 1. 依赖处理（API 层固定准则）

| 依赖类型                                       | 默认策略                                                                                   |
| ---------------------------------------------- | ------------------------------------------------------------------------------------------ |
| **被测服务自己的 DB / cache / MQ**             | **真实**——mock 内部 IO 会让前门退化为"通过 mock 不通过现实"的假绿                          |
| **外部不可控依赖**（第三方 / 跨服务）          | fake / 录制回放 / **CDC**（跨服务 gRPC / HTTP 优先 CDC，录制回放遇协议变更会沉默失败）     |
| **业务契约级外部依赖**（业务文档会描述其触达） | fake，且具备**调用记录能力**——查"是否触达 + 关键业务参数"，**不暴露次数 / 顺序作为断言面** |
| 时间 / 随机 / UID                              | 注入抽象，用例固定值                                                                       |
| 内部纯函数                                     | 不替换                                                                                     |

每处 fake 必须能回答：**"为什么替换，替换后还能暴露什么真实退化"**——否则不写。

### 2. 数据策略

- 等价类：成功 / 业务拒绝 / 系统异常
- 边界点：数值、长度、时间、并发、容量
- 共享 fixture vs 内联：稳定上下文共享；行为差异点必须内联
- 不可控输入：时间用注入接口、随机固定 seed、UID 显式传入

### 3. 测试隔离策略（必须显式声明）

二选一：**事务回滚**（每用例包事务结束 rollback；简单，限制并行）/ **数据集合分桶**（用例间不共享 ID 命名空间；适合并行）。

> **反模式**：靠"反正每条 cleanup 一下"——规模上去会因 cleanup 漏写 / 顺序问题崩盘。隔离必须由测试基础设施统一兜底。

### 4. 风险地图

变更覆盖（diff 路径）/ 回归区（历史 bug 集中处）/ 隐式边界（时区、并发、Unicode、null/空、精度、字节边界）/ 跨模块语义一致性 / **横切契约**（鉴权、租户隔离、限流——若产品契约的一部分而非框架透明处理）。

## 五、断言通道：前门优先，后门兜底

### A · 前门通道（默认）

按 API 实际可观察面挑最自然的；**多通道协同**（response + 反向读 + 副作用三角）比单通道信心高，关键路径值得做。

**a) Response 直接观察**——状态码 / body / 契约级 header（`Location` / `ETag` / `Cache-Control` / 版本号）/ 生成的 ID。**第一眼就该问的地方。**

**b) 配对反向读接口**——同一系统的 `GET` / `list` / `info` / `status`，本质是"用另一个 API 的 response 观察"。
> **缓存场景纪律**：涉及自身缓存的写接口，关键路径采用 `预读 → 改 → 再读` 序列。只 `改后读` 会因首读未建缓存而让漏清缓存的 bug 沉默。这是"写后读拿到新值是契约"在缓存语境下的可执行形态。

**c) 依赖该状态的其他业务接口**——用系统其他业务路径作为"状态镜"（feature flag SET → 业务接口行为切换；权限 SET → 受保护资源访问）。**顺带验证状态被系统正确消费**，比 b) 信心更高。

**d) 业务契约级外部触达**——事件 / 邮件 / webhook / 推送 / 合规审计（业务文档承诺过的）。断言"是否触达 + 关键业务参数"，**不断言次数 / 重试间隔 / 协议字段顺序**。

> **使用 d) 时的二分判据**：脱离代码看，外部用户 / 产品方**会不会感知到这个调用的存在**？
> - **业务契约**（会感知，如"开户必须通知风控"）→ 断言触达 + 关键参数
> - **实现机制**（不会感知，如"为刷缓存调 Redis"）→ 不断言

### B · 后门通道（兜底，慎用）

**仅当 A 中所有前门通道都真不可用**（write-only 接口、内部审计字段无对外查询路径，且 C 段设计反馈被产品方拒绝）才走后门。要求：

1. 直接查持久存储 / 缓存的最终态
2. 必须封装为**业务语义命名的 helper**（如 `assertOrderPersisted(orderID)`）
3. **helper 放独立 fixture / verification 模块**，用例文件里**不直接出现** `db.Query(...)` / `redis.Get(...)`
4. 必须**显式标注"走后门的理由"**
5. 接受 scope 已下沉为 "API + 存储集成"

**后门盲区警告**——DB 对了 ≠ 对外可见，下面四类 bug 后门验证都看不到：

- 写主库成功，忘了 invalidate 缓存 → 调用方读到旧值
- 写主库成功，读副本同步延迟 → 调用方拿不到
- 写存储成功，搜索索引未更新 → 列表 / 搜索接口查不到
- 写实体成功，事件未发出 → 下游永远不知道

> **能走前门就别走后门**。前门多花点功夫，顺带验证一致性 / 可见性 / 缓存同步 / 索引更新整条对外链路；后门只能告诉你"DB 这一格被填上了"。

### C · Write-only 接口：设计反馈优于测试技巧

遇到"前门 a-d 全无可观察面"的 SET 接口，**先把它当成设计问题报上去**——推动加 `GET` / `list` / `status`、加 admin / debug 端点（声明属于运维契约）、在 response 或事件里暴露更多状态。

> "无法被黑盒测试"是一种重要的设计反馈。**测试的第一价值是推动设计改进，不是绕过去测出"看起来通过"的结果。**

只有产品方明确拒绝扩展契约时，才退回 B 段后门。

## 六、用例维度（统一表）

> **所有维度都是契约维度**（核心目标仍是验证对外契约，后门只是兜底通道）。1-6 由业务规格触发，7-9 由技术上下文触发——只写"该契约是否对外正确兑现"，不写"内部机制怎么实现"。

| 维度                                              | 何时写 / 不写                                                                            | 提示用例数          |
| ------------------------------------------------- | ---------------------------------------------------------------------------------------- | ------------------- |
| **1. 核心业务规则**                               | 默认写；不写：已被更上层等价覆盖                                                         | 主体覆盖            |
| **2. 异常路径与容错**                             | 业务有失败语义；不写：异常框架统一处理且无业务分支                                       | 关键路径            |
| **3. 边界条件**                                   | 涉及数值 / 长度 / 时间 / 容量的端点；不写：类型 / 编译期已约束。                         | 按风险              |
| **4. 状态流转 & 幂等**                            | 接口有状态；不写：无状态；或幂等由协议层兜住且无业务侧校验                               | 按状态机            |
| **5. 输入校验**                                   | 业务有校验语义；不写：校验在独立模块且本接口透传                                         | 关键路径            |
| **6. 横切契约**（鉴权 / 租户 / 限流）             | 是产品承诺；不写：框架透明处理且无产品承诺                                               | 每类 1-2 条         |
| **7. 副作用契约**（事件 / 邮件 / webhook / 审计） | 业务文档承诺触达；**不属于业务契约的内部调用永不写**                                     | 每个契约 1 条       |
| **8. 缓存契约**                                   | TTL 过期 / 跨写中间态 / `Cache-Control` / 304 等明确对外承诺；多数情况下反向读再读已覆盖 | 仅特殊承诺时 1-2 条 |
| **9. 事务原子性**                                 | 跨依赖写入有半提交风险；不写：单一存储或无半提交风险                                     | 1-2 条              |

> **反例：状态枚举 / 互斥前置条件的成功路径属于维度 1 的等价类划分，不是维度 3**
> **纪律**：所有维度的用例 Then 段**不**出现 cache key、Redis、SQL 列、调用次数等技术词。
> **不主动凑数**：触发条件不满足就不写，并在"为什么不写"清单里说明。

## 七、用例格式（弱约束）

**最小必填**：
- **目的**——一句话说"在防什么退化"，业务语言
- **前置（Given）**——上下文 / 依赖状态；mock 单列子项（依赖 / 替换值 / 为什么这一层 mock）
- **触发（When）**——动作 + 关键参数
- **断言（Then）**——外部可观察的输出 / 状态 / 事件

**表达方式**：Gherkin / 数据驱动表格 / 状态矩阵。**首次产出请读 `references/example.md` 取格式样板。**

## 八、反模式

**【哲学层】原则 1/2/3 的常见违反**
- 跳过 STEP 0.5，从源码风险登记直接跳到用例 → 必然把实现机制误当契约
- 业务行为没变、纯重构就大批挂掉 → 写穿到机制层，把 assert 抬回契约层（**不是**删 fixture）
- 混淆"耦合实现"和"依赖实现" → fixture 用 ORM 直插 DB 是耦合（手段、可接受）；assert 出现 `redis.Exists(key)` 是依赖（机制、不可接受）

**【通道选择层】**
- 跳过前门排查直接走后门
- 后门验证当全套断言（盲区：缓存未清 / 副本延迟 / 索引未更新 / 事件未发都看不到）
- 遇 write-only 接口默认走后门，而不先反馈设计问题

**【用例设计层】**
- 一个用例验证多件事 / 用例间隐式顺序依赖
- 追求覆盖率百分比而非风险 / 为代码里看到的每个分支造一条用例
- mock 内部纯函数 / mock 被测服务自己的 IO
- 共享可变 fixture 不重置 / 用真实当前时间 / 未固定 seed
- 用例描述只写"测试 XXX 函数"
- 所有依赖都 mock 成功路径，无失败路径用例
- **假多样性**：多个用例只在 mock 配置上不同 → 合并；或找到真正不同的业务前置作为差异化点
- **snapshot 全量响应** → 只对契约字段做 snapshot

## 九、自检清单

### Per-case
- [ ] 失败信息会指向**被破坏的业务规则**还是**内部调用没发生**？后者必须改写
- [ ] 与最近一条用例的差异，是 **mock 配置**还是**真实退化**？仅 mock 配置不同就合并
- [ ] **观察面层级**：前门（response / 反向读 / 联动 / 业务级触达）还是后门？走后门是否封装了语义化 helper、显式标注理由？前门 a-d 是不是真的都不可用？
- [ ] **失败可见性**：如果代码漏掉一类清理 / 失效 / 联动操作（缓存清除、索引更新、事件发出），这个用例的断言序列还能让它失败吗？不能就需要补预读 / 加联动读 / 加副作用断言
- [ ] **多通道协同**：能否同时断言 response + 反向读 + 业务级副作用？关键路径值得做三角验证
- [ ] **重构韧性**：业务行为不变、纯重构内部，这条用例还该过吗？该挂 = 改
- [ ] **setup vs assert 分离**：所有"耦合实现"的点都关在 setup 里？

### 总检
- [ ] 业务事实清单存在，**每条业务规则用例可追溯到清单中某一条**
- [ ] 维度 1-6 与 7-9 各自的触发条件已判断；不满足的已在"为什么不写"中说明
- [ ] 缓存维度（8）用例 ≤ 2 条且独立成节
- [ ] 副作用契约（7）只对"业务文档会描述的调用"写
- [ ] 不存在跨用例顺序依赖，隔离策略已落实
- [ ] 外部依赖按二分（实现机制 / 业务契约）正确处理；内部 IO 一律真实
- [ ] 覆盖了变更点 + 历史 bug 区 + 横切契约（如适用）
- [ ] 所有维度都有取舍说明（含"为什么不写"）

## 十、输出形态

**三段式产物**。第一段未写完不进策略；策略未澄清前不进用例。

- **第一段 · 业务事实清单**——3-7 条业务定义级承诺，纯业务语言；每条用例可追溯回此清单
- **第二段 · 测试策略摘要**——被测对象 + 范围 / 依赖处理（逐依赖：真实 / fake / CDC / 注入抽象 + 理由）/ 数据策略 / 隔离方案 / 风险地图
- **第三段 · 用例清单**——按维度组织，每条追溯到第一段清单某条；末尾必含 **"为什么不写"清单**——被主动放弃的覆盖点 + 理由
